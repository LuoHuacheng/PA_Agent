## 2. 拦因分层

### 2.1 session_block（主因，15/17）

配置（`config/settings.json` → `binance_usdm_testnet`）：

| 键 | 值 |
|---|---|
| `block_session_entry` | `true` |
| `block_session_utc_start_hour` | `20` |
| `block_session_utc_end_hour` | `4` |

判据是左闭右开 `[20:00, 04:00)` UTC，即 **04:00–11:59 UTC+8** 全禁进场。
02:14 UTC 时点落在窗内，12:00（UTC+8）自动解锁——这解释了为什么"越跑越静"。
同一段墙钟时间在 2026-09-19 之前写作 `04:00-11:59 UTC+8`，改为 UTC 口径后属于同一窗口，
既有 45 天回放证据（`logs/shadow_rows_*.csv`，禁该窗口 +57.59U）继续沿用。

### 2.2 rr_block（4 拦）

`min_plan_reward_risk=1.5`，判据是 **TP1** 距入场 ÷ 止损距离
（`_entry_block_reasons` 传给 `compute_risk_reward` 的是 `take_profit_price`，不是 TP2）。
窗内三条都只差一点：03:31 ETH `1.47`、07:31 SOL `1.42`、04:31 BTC `1.31`。

以 04:31 BTC 实算校验：entry 86490.11、stop 85799.0、TP1 87395.67
→ (87395.67 − 86490.11) ÷ (86490.11 − 85799.0) = 905.56 ÷ 691.11 = **1.31** ✓。

**与 TP2 上限无关**：同轮日志里 `max_plan_reward_risk_tp2=3` 收窄的是 `take_profit_price_2`
（88874 → 88563.44，恰好 = 3.0R），`rr_block` 不读 TP2。
真正值得记的是：这个下限**提示词已经明示给模型**（`prompt_assembler.py` 的「程序侧硬约束」块
写着「TP1 距入场不得小于 止损下限 × 最小盈亏比」），所以 1.31–1.47 是模型没遵守已声明约束，
而不是程序口径自相矛盾。

### 2.3 cycle_block（1 拦）

02:31 BTC 的 `cycle_position=tight_channel` 不在白名单 `broad_channel / normal_channel / trading_range`，
这是窗内唯一与时间窗无关的拦截。

### 2.4 模型侧自我弃权（09:31 之后 0 方案）

09:31 起到 10:03，5 个品种全部输出 `order_type=不下单`，**连门控都碰不到**。
10:03 ZEC 的理由原文：做多逆 §2.4 弱空头、做空与日线偏多（7 天 +42%）相反，
"执行层逆势闸门直接拒单"。提示词把闸门后果写进了决策依据，模型提前自我审查 → 弃权。

这一段不是"被拦"，而是"没送上桌"：门控统计里看不见，只有 `[决策] ... 类型=不下单` 行。

## 3. 为什么体感是"全被拦"：门控短路

`SignalPipeline.evaluate()` 先算入口门控，命中即 `return`，**方向闸门根本不执行**：

```python
env_reasons = self._entry_block_reasons(inner, decision=decision)
if env_reasons:
    ...  # 记录 gate_blocked + 推送, 直接返回
reasons = self._direction_gate_reasons(...)  # 永远轮不到
```

后果：`session_block` 一开就吞掉整段窗口，`direction_gates_mode=on` + `counter_trend_block=true`
是否也会拦同一批单，**在这 8 小时里无从判断**。排查时看到的"一个原因解释全部"，
是短路造成的观测遮蔽，不是市场真的只剩一个 fail 点。

## 5. 附带发现（已修 / 待议）

### 5.1 已修：门控文案的 UTC 末分钟差一小时

旧代码把 `end_hour_utc` 直接当末分钟打印：

```python
# 旧: f"-{end:02d}:59 UTC" -> 20:00-04:59 UTC
# 新: _session_window_label(start_hour_utc=20, end_hour_utc=4) -> 20:00-03:59 UTC
```

实际窗是 `[20:00, 03:59]` UTC，文案却写 `04:59`，照它换算北京时间会多算一小时。
2026-09-22 抽出纯函数 `_session_window_label()`（左闭右开的末分钟 = `end-1:59`），
并加回归测试 `test_session_window_label_is_inclusive_last_minute`；
`test_block_session_entry` 追加断言 `03:59 UTC in reason` 且 `04:59 not in reason`。

### 5.2 待议：session_block 的证据强度

`docs/近10小时未下单归因与放行反事实.md` §4 对它的裁定是**证据不足**——拦下的单在挂单口径 0 成交，
既没拦错也没拦对。本次 15 次拦截同样产生不了可评估样本（窗内本来就不允许挂单）。
要动它，得先设计窗内反事实回放，而不是拿"这 8 小时没信号"当依据。

### 5.3 待议：TP2 收窄与 RR 门槛的耦合

见 §2.2：`max_plan_reward_risk_tp2` 收窄远端目标会同步降低 `compute_risk_reward` 的 ratio，
见 §2.2：TP1 下限已通过 `prompt_assembler.py` 的「程序侧硬约束」块明示给模型，
本窗口 3 条仍差 0.03–0.19。可选路线：(a) 维持门槛、加强提示词遵守率；
(b) 下调 `min_plan_reward_risk`；(c) 像 `max_rr` 管 TP2 那样，把 TP1 下限改成程序侧自动外扩，
用归一化替代模型自觉。三条都缺回放证据，本文不裁决。

## 7. 局限

- **样本重叠**：17 条拦截来自 5 品种 × 16 个 30m 周期，同一波行情被反复采样；去重叠后独立样本个位数。
- **无窗内反事实**：窗内不允许挂单，故本窗口无法评估"放行 session_block 会不会更好"。
- **观测遮蔽**：入口门控短路导致方向闸门命中数在窗内恒为 0，`config/monitoring_state.json` 的
  `direction_gate_stats` 在窗内只反映入口门控，不能当方向闸门的效果指标读。

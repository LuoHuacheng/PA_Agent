# 撤单复盘与挂单参数评估

日期：2026-09-10　窗口：2026-09-09 23:02:40 — 2026-09-10 11:02:40（CST）

## 1. 为什么要做这件事

对过去 12 小时的撤单做归因时，发现两个工程问题：

1. `logs/pa_agent.log` 轮转保留 5 MB × 10 个文件，按当前日志量只覆盖约 9.8 小时，
   12 小时窗口的头部（23:02—00:35）已经被滚掉，只能靠推断。
2. 撤单事件只以自由文本出现（`resting remainder canceled` / `Replaced stale ...`），
   要按原因统计必须手工 grep 多个轮转文件。

本文件记录当时的评估结论与随后的改动，便于以后复算。

## 2. 数据

把全部可用日志里的「挂单」与后续结局配对，得到 54 笔完整样本：

|------|------|

成交耗时（17 笔）：中位 **14.4 分钟**，p90 **约 56 分钟**，最长 57.9 分钟。

12 小时窗口内实际撤单 7 笔：5 笔超时撤销、2 笔被新方案替换。

同价位重挂：46 组相邻挂单中 8 组（17%）与上一单价差不超过 0.05% 且间隔不超过 90 分钟，
其中 4 组价格完全相同（ETHUSDT 2499.74→2499.74、2486→2486；SOLUSDT 106.47→106.47 连续两次）。

## 3. 结论：`limit_fill_timeout_minutes=60` 保持不变

60 分钟超时切掉的正好是长尾两端：成交样本里有两笔在 55.6 / 57.9 分钟才成交。
缩短到 45 分钟会丢约 12% 的成交，而超时本身并不产生亏损（挂单未成交即撤），
真正的浪费是「撤单后立刻同价位重挂」，因此不在超时上动手，改在轮换行为上加闸门。

参数对照：15m 周期下 60 分钟 = 4 根 K 线；当前监控使用 30m 周期，60 分钟 = 2 根 K 线。
若后续把监控周期拉长到 1h 以上，应重新评估该值。

## 4. 已实施的改动

### 4.1 撤单审计（`records/cancels/*.jsonl`）

每次撤单（成功或失败）都会追加一条 JSON：

```
{"ts_ms":1789000000000,"ts_iso":"2026-09-10T09:32:40","symbol":"SOLUSDT",
 "client_id":"pa-entry-42cb9051fbd76ea8b028db09d54","reason":"limit_entry_timeout",
 "detail":"timed out","environment":"Testnet","entry_price":"101.75","signal_id":"..."}
```

`reason` 为稳定枚举，只增不改：

- `limit_entry_timeout` — 限价挂单超时未成交，程序撤销（含 `timed out after status failures`）。
- `plan_replaced` — 新一轮分析给出新方案，旧的 resting 挂单被替换。
- `stale_entry_removed` — 交易所已无此单（-2013），本地挂单记录被清除。
- `cancel_failed` — 撤单请求被拒绝，旧挂单仍留在交易所，pending 记录保留待重试。

实现：`pa_agent/records/cancel_log.py`；埋点在 `binance_usdm_testnet._cancel_and_settle`
与 `_replace_pending_limit`。审计写入是 best-effort，失败只记 warning，绝不影响下单流程。

按原因统计一行命令：

```bash
cat records/cancels/cancels-*.jsonl | python -c \
  "import sys,json,collections;print(collections.Counter(json.loads(l)['reason'] for l in sys.stdin if l.strip()))"
```

### 4.2 日志保留期加长

`pa_agent/util/logging.py`：`maxBytes` 5 MB × `backupCount` 20（约 100 MB，覆盖约 18 小时），
保证 12 小时复盘窗口在原始日志里也读得到；`records/cancels/` 是长期凭据。

### 4.3 同价位轮换冷却

新增配置（`settings.json` → `binance_usdm_testnet`）：

- `limit_repricing_min_ticks`（默认 3）— 与上一笔被撤挂单的价格相差不超过几跳算「同价位」。
- `limit_repricing_cooldown_minutes`（默认 30）— 撤单后该价位带的静默时长。

任一参数取 0 即关闭该闸门。命中时 `execute` 返回 `skipped`，原因写入日志与执行结果，
不挂新单；旧挂单若已被撤销则保持空仓等待，不会追价。锚点写入运行时状态文件
`last_canceled_entries[symbol] = {entry, reason, ts}`。

## 5. 复现方式

```bash
# 撤单明细（窗口内）
grep -E 'canceled|Replaced stale' logs/pa_agent.log*
# 结构化的撤单账本
ls records/cancels/
```

历史配对统计脚本按「挂单 → 成交/超时/替换」三次配对计算，样本来自
`logs/monitor_console.log`（15m 周期阶段）与 `logs/pa_agent.log*`（30m 周期阶段）。

## 6. 后续观察点

- 冷却命中率：若 `skipped` 占比过高（例如超过挂单尝试的 20%），说明阈值偏紧，可下调 ticks 或缩短窗口。
- 30m 周期下的成交率：窗口内 6 笔挂单 0 成交，若持续为 0，需要回到「entry 挂得是否太远」这一策略问题。
- 日志量增长后重新核对保留时长（当前约 5.6 MB/小时）。

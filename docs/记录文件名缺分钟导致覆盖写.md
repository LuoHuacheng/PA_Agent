# 记录文件名缺分钟导致覆盖写（2026-09-21 根因）

> 症状表现是「漏轮」：`records/pending/` 里某些整/半点没有记录，看起来像监控少跑了一轮。
> 实际**每一轮都跑了**，是**落盘文件名冲突**把前一轮覆盖掉了。

## 1. 根因

`pa_agent/records/pending_writer.py` 的 basename 构造：

```python
ts_str = dt.strftime("%Y-%m-%d_%H-%m-%S")   # %m = 月份, %M 才是分钟
```

文件名格式因此是 `日期_时-月-秒_品种_周期`，**丢了分钟**。同一小时内两轮（HH:00 与 HH:30）
只要 meta 时间戳的「秒」相同，文件名就逐字节相同，后一轮静默覆盖前一轮（`Path.write_text` 覆盖写，无告警）。

9 月时 `%m` 恰好是 `09`，文件名看起来完全正常；读文件的代码按 `%M` 解析则一律读成「9 分」
——所以这个 bug 既不报错，也很难被肉眼发现。

## 2. 证据链

窗口：`2026-09-20 20:41`（GATE_START，节拍 30min）～ `2026-09-21 11:00`，5 品种。

### 2.1 日志说跑了 145 轮，磁盘只有 130 份记录

| 项 | 值 |
|---|---|
| `Monitor analysis completed` 行数 | **145** = 29 轮 × 5 品种 |
| 落盘记录数（按 bar 去重） | **130**（BTC 23 / ETH 25 / LINK 29 / SOL 24 / ZEC 29） |
| 丢失 | **15**（BTC 6 / ETH 4 / SOL 5；**LINK、ZEC 0**） |

### 2.2 单点铁证（BTC 03 点）

- 日志：`03:00:05 Monitor analysis started for BTCUSDT` → `03:02:01 [决策] BTCUSDT 类型=不下单` → `analysis completed`。
- 磁盘：03 点整小时只有**一个** BTC 文件 `2026-09-21_03-09-09_BTCUSDT_30m.json`，其 meta 是 **03:30:09.639**。
- 两轮 meta 的秒都是 09 → 名字都是 `2026-09-21_03-09-09_BTCUSDT_30m` → 03:30 那轮覆盖了 03:00 那轮。
- 03:30 记录的 `stage1_messages` 长度 = 5（增量链），说明它读到并沿用了 03:00 那轮的 prompt —— 即 03:00 记录**当时确实存在**。

### 2.3 对照组：LINK / ZEC 一轮不丢

| 品种 | 波次 | 启动秒 | 丢失 |
|---|---|---|---|
| BTC / ETH / SOL | 第一波（`max_concurrent_analyses=3`，固定 :00:05 / :30:05） | 由固定流程决定，**常常相同** | 15 |
| LINK / ZEC | 第二波（等前一波释放线程，:01–:03 且逐轮抖动） | 不规则 | **0** |

同一份代码、同一节拍，唯一差别是「启动秒是否系统性重合」，丢失率就从 21% 变成 0 —— 这是文件名冲突的判别性证据。

### 2.4 复现（修复前）

```python
build_record_basename(meta_at(2026-09-21 03:00:09.639))  # 2026-09-21_03-09-09_BTCUSDT_30m
build_record_basename(meta_at(2026-09-21 03:30:09.639))  # 2026-09-21_03-09-09_BTCUSDT_30m  ← 同名
```

## 3. 影响面

| 影响 | 说明 |
|---|---|
| 决策链路 | **无**。覆盖只发生在写盘；`find_latest_successful_record` 按 **mtime** 排序（`analysis_history.list_record_paths`），读上一轮时它还在，增量链没断 |
| 样本计数 | **有**。`R2/R3` 判定、`daily_check` 的「上线后 n 条」、各类归因统计都按记录文件数算，最近 14.5 小时少算约 **10%**（15/145） |
| 历史文件解析 | **有**。`experience_reader._parse_timestamp_ms` 与 `outcome_store` 按 `%M` 解析文件名，把月份 09 当成分钟 |
| 数据可恢复性 | 被覆盖的 15 份记录内容已丢失，只能从日志确认「跑过」 |

## 4. 修复

| 文件 | 改动 |
|---|---|
| `pa_agent/records/pending_writer.py` | 抽出 `build_record_basename(meta)`，`%m` → `%M`；`_build_basename(record)` 保留为薄包装 |
| `pa_agent/orchestrator/free_chat.py` | `_derive_record_id` 改为委托同一函数（原实现复制了同一处 `%m` bug，命名口径必须唯一） |
| `tests/unit/test_pending_writer_filename.py` | 新增回归测试：文件名必须含分钟；同小时同秒两轮不得同名；两次 `save_full` 必须留两个文件 |

**生效条件：需要重启监控进程**（当前 pid 85082 跑的是旧代码）。重启前新记录仍可能继续互相覆盖。

修复后：

```text
03:00:09 -> 2026-09-21_03-00-09_BTCUSDT_30m
03:30:09 -> 2026-09-21_03-30-09_BTCUSDT_30m    # 不再同名
```

## 5. 顺带订正

本次排查推翻了两条此前写下的判断：

1. `docs/消息结构切换决策材料.md` §2.2 曾写「12 个全量轮次来自起服首轮 + 漏轮」——**并不存在漏轮**。
   12 轮 = 5 端起服首轮 + 5 轮紧随 02:00 那批 `stage1 network_error` 半成品记录 + 2 轮（BTC/SOL 22:00）紧随 21:30 的同类半成品。
   即：全量重建的触发原因只有「首轮」与「上一轮 stage1 失败」两种。
2. 曾经出现的「间隔 60min」是**统计口径造成的假象**：早先脚本过滤掉了无 `usage_total` 的半成品记录，
   21:30（半成品）被跳过，21:00 与 22:00 看起来就相隔 60min。按 bar 口径重算，真实缺口正是上表那 15 个。

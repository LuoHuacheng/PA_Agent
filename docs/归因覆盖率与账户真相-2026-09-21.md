# 归因覆盖率与账户真相 (2026-09-21)

> 承接 [账户成交与outcomes对账](./账户成交与outcomes对账-2026-09-21.md). 那篇查明
> outcomes.csv 只覆盖账户损益的 8%. 本篇做两件事: 把"账户真相"与"归因覆盖率"变成
> 随时可见的数, 并查清 917 条交易腿里 892 条"未归因"到底是什么.

## 1. 归因分层实测 (30 天窗口)

`tools/outcome_merge.py --days 30` 实测:

| 状态 | 腿数 | 净额 |
| --- | --- | --- |
| matched | 24 | +34.08U |
| manual | 817 | -399.55U |
| missing_decision | 1 | +26.22U |
| ambiguous | 0 | 0.00U |

只看这一行, 结论会是"归因率 24/842 = 2.9%, 没法用". 但这个读法是错的.

## 2. 根因: "manual" 不是人工单, 是订单历史过期

两条硬证据:

1. **交易所订单列表只回溯约一周**. 实测 `/fapi/v1/allOrders` 最早只能看到
   **2026-09-15 12:01**, 更早的成交腿查不到 clientOrderId, 于是 `attach_decisions`
   把它们归成 `manual`(cid 无法解析), 而不是"人工下单".
2. **本地订单账本 2026-09-18 才开始记**. `records/orders/` 只有 4 个文件
   (09-18 -> 09-21, 共 55 行), 覆盖不了更早的挂单.

按开仓时间切开, 分界干净得像刀口:

| 开仓时间 | pa-entry 前缀 | 未解析 | 净额 |
| --- | --- | --- | --- |
| < 2026-09-16 | 5 | **892** | -2126.18U |
| >= 2026-09-16 | **11** | 0 | +9.40U |
| >= 2026-09-18 | **9** | 0 | +64.81U |

**09-16 之后的交易腿 100% 解析出了 pa-entry.** 所以归因机制本身是好的, 892 条是
"证据已经过期"的观测窗口问题, 不是策略或归因逻辑的问题.

## 3. 修复一: 覆盖率必须与结论一起报

新增 `pa_agent/feedback/outcome_store.py`:

- `dedupe_income_rows` / `income_net_by_symbol` —— 账户真相(按品种).
- `cid_visible_from` —— 每个品种 allOrders 能看到的最早订单时间, 即"归因窗口"下界.
- `account_coverage` —— 三层口径 + 两层覆盖率 + manual 拆分.
- `_cid_window_coverage` —— 把 manual 拆成"订单历史过期"与"真外部单", 并给出
  **窗口内归因率**.

挂在 `build_audit_summary` / `merge_all` 上, 所以写进
`logs/outcome_audit_YYYYMMDD.json`; `tools/outcome_merge.py` 现在直接打印:

   账户真相(income): 全账户 -1963.64U | 策略范围 -258.89U | 策略外 -1704.75U
     策略外最大 5 项: HEMIUSDT=-1670.06U, SKRUSDT=-24.12U, LTCUSDT=-22.18U, ...
   归因覆盖率: 第1层(全部) 24/842 | 第2层(订单可见窗口内) 24/25
     manual 拆分: 订单历史过期 817 条 -399.55U | 真外部单 0 条 0.00U

**第 2 层 24/25 = 96% 才是该看的数**: 证据还在的有效窗口里, 归因几乎不漏.

## 4. 修复二: income 流水被重复累加 (真 bug)

`tools/outcome_merge.py` 按品种循环调 `fetch_account_data(client, [sym], ...)`, 但
`client.income_history()` **不带品种过滤** —— 它每次返回整个账户的流水, 循环里又
`account["income"].extend(...)` 了 N 次. 结果是:

- 账户真相被放大 **N 倍**(N = 本次范围的品种数, 实测 10);
- 打印的 `income 对账` 全是错的(量级就不对).

修法: `merge_all` 里对 income 去重(`dedupe_income_rows`, 优先 `tranId`, 缺失时退回
时间+品种+类型+金额+资产). 修完 `income 对账` 每品种差 0.8 - 15.4U(合计约 -80U),
量级终于合理 —— 那点差是 LIFO 配对误差加资金费, 不是口径错.

## 5. 顺带确认: outcomes.csv 不会因重跑缩水

`write_outcome_csv` 是按 `uid` 合并追加再整体重写, **不是覆盖**. 实测重跑前后都是
107 行. 所以历史归因行不会被今天的(较短)可见窗口抹掉 —— 这一点决定了"重跑安全".

## 6. 结论

1. **别再用第 1 层归因率**(2.9%) 说事. 它主要由订单历史可见性决定, 与策略质量无关.
2. **要报就报第 2 层**(订单可见窗口内): 当前 96%, 且这是唯一可以持续变好的指标.
3. **提高归因率只能靠"从现在开始"**: 账本已在记(09-18 起), 交易所可见窗口约一周,
   两者叠加后新交易天然高覆盖. 历史那 817 条追不回来.
4. **账户真相一律用 income 流水**, 且必须去重; 策略范围与策略外要分开报.
   当前 30 天: 全账户 -1963.64U, 策略范围 -258.89U, 策略外 -1704.75U
   (HEMIUSDT 一个品种 -1670.06U = 85%).
5. `outcomes.csv` 应显式标注为"归因覆盖窗口内的子集".
